# PR 审查判断规范

## 如何形成问题结论

- 对照 PR 的真实目的检查改动。把新增问题、既有问题与无法确认的业务假设分开；仅将本次引入或明确加重的问题作为 PR 发现。
- 每个问题必须能回答：什么输入/状态触发，经过什么代码路径，导致什么错误，以及本次改动为什么造成它。查阅周边实现和调用方，排除已有保护。
- 权限路径、配置变动、依赖更新、删除测试、`any`、`TODO` 和大 diff 都只是排查线索，不能单凭关键词认定缺陷。
- 证据不足时继续按需读取代码；仍不能确认则列为待确认事项，不降级包装成一个确定的低风险 bug。
- 只报告作者有理由修复的问题。避免格式偏好、推测性的重构、泛泛“补充测试”和重复发现。

## 与正确使用有关的检查

按变更实际涉及的内容选取，不机械地逐项检查整个仓库：

- 功能：调用方是否满足新参数/返回值，空值和边界输入，异常传播、资源释放，异步顺序及重试是否改变行为。
- 权限与数据：输入来源和校验位置、授权是否覆盖目标对象、敏感数据是否进入响应或日志、失败路径是否绕过限制。
- 集成：配置默认值、依赖版本、迁移顺序、旧调用方式、部署环境和跨模块契约是否匹配。
- 验证：已有测试是否覆盖实际修改路径；测试通过是否只是未触达问题分支。需要时做一个最小复现，而不是启动与变更无关的完整测试套件。

## 严重程度与位置

- P0：广泛且无条件的严重故障，需要立即处理。
- P1：明确的核心功能、安全或数据问题，通常应在合并前修复。
- P2：在具体条件下触发的真实缺陷，需说明条件和影响。
- P3：影响较小但具体可修复的问题；不为充实报告主动寻找这一类。

定位到 diff 中最小的相关行段。新增/修改使用 head 行号，删除使用 before 行号；有必要时补充调用方链接。无法验证行号时说明缺少定位证据，不编造数字。固定提交链接优先于会随分支更新的链接。

## 报告例式

```text
结论：发现 1 项阻碍，建议修复后验证。审查版本：<head SHA>。

[P1] <具体问题> — <文件位置链接>
在 <输入/状态> 下，<代码路径> 会导致 <实际后果>。
证据：<实际代码与关联调用，不重复问题标题>。
建议：<最小修正方向及必要的验证场景>。

验证：<真实执行的命令或操作与结果>。
覆盖：<审查过的内容及影响判断的限制>。
```

没有发现时使用“在已审查范围内未发现需要修改的问题”。检查范围完整且相关运行验证成功时，可以说明这些路径已验证可用；依然不要把单个测试或静态审查推广为所有场景保证。

## 数据脚本边界

- GitHub PR files 接口最多返回 3,000 个文件，脚本按每页 100 个请求并核对总数；超出范围必须补充 Git diff 或限制结论。
- patch 的行数及 hunk 校验用于发现缺失/截断，不替代完整文件和调用关系分析。无文本 patch 可能来自二进制、重命名或 API 限制。
- 文件读取固定 SHA；before 使用 merge-base，head 优先使用 fork 仓库。源 fork 已删除时尝试在目标仓库读取同一提交，失败则说明内容不可用。
- `check` 只核对 base/head SHA，不证明 CI 通过、具备合并权限或代码正确。
- GitHub API 参考：[PR 文件分页](https://docs.github.com/en/rest/pulls/pulls#list-pull-requests-files)、[固定 ref 读取内容](https://docs.github.com/en/rest/repos/contents#get-repository-content)、[提交比较](https://docs.github.com/en/rest/commits/commits#compare-two-commits)。
